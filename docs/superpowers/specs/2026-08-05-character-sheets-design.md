# Настоящие листы персонажей вместо оценок

## Зачем

Сейчас программа знает про персонажа только класс и уровень, а всё остальное
выводит. Это осознанный выбор: когда делался калькулятор боя, я отказался
спрашивать характеристики, потому что просить у четырёх друзей бонус атаки и
хиты — верный способ, чтобы ботом перестали пользоваться.

Но у оценки есть цена, и она уже мешает:

* лист партии считает роли по **всему списку класса**, поэтому для барда и
  чародея завышает: они знают лишь несколько заклинаний из сотни доступных;
* калькулятор боя оценивает AC, хиты и урон по классу и уровню, и ошибается
  тем сильнее, чем необычнее сборка;
* в отряде есть люди, которые ботом не пользуются, и посчитать их нечем.

Задача — дать возможность вводить настоящие данные, **не сломав работу без них**.

## Главный принцип: цепочка отката

Каждое число персонажа берётся по порядку:

1. явно введённое значение (`AC 17`);
2. выведенное из характеристик (Ловкость 16 → +3 к AC и спасброскам);
3. оценка по классу и уровню — то, что работает сегодня.

Заполнить можно сколько угодно и в любом порядке. Ничего не заполнил — ведёт
себя как сейчас. Это одно место в коде, а не проверки «если задано» по всему
проекту.

## Владелец ведёт отряд, а не только себя

Основной сценарий — один человек заводит и правит всех, потому что остальные
ботом не пользуются. Присоединение по коду остаётся, но становится
второстепенным.

Отсюда смена схемы: персонаж перестаёт быть жёстко привязан к аккаунту.

```
characters(
    id            INTEGER PRIMARY KEY,
    owner_id      TEXT NOT NULL,     -- кто ведёт запись
    telegram_id   TEXT,              -- NULL у заведённых вручную
    name          TEXT NOT NULL,
    class_key     TEXT NOT NULL,
    level         INTEGER NOT NULL,
    party_code    TEXT,
    str, dex, con, int, wis, cha  INTEGER NULL,   -- характеристики
    ac, hp, attack_bonus, damage  INTEGER NULL    -- переопределения
)
character_spells(character_id, spell_key)
```

Существующие записи мигрируются: старая строка становится персонажем с
`telegram_id = owner_id`. Терять данные друзей нельзя, их уже завели.

## Заклинания: один список

Разделения на «известные» и «подготовленные» не будет. Для вопроса «чего
партии не хватает» важно только то, что персонаж **может применить сегодня**;
два списка удвоили бы ввод ради различия, которое здесь ничего не решает.

Когда у персонажа есть свой список, лист партии считает роли по нему, а не по
списку класса. Это и есть то, ради чего всё затевалось.

## Паритет интерфейсов

Всё, что можно сделать на сайте, можно сделать и командой в боте. На сайте
формы и поиск по списку — так быстрее забить два десятка заклинаний; в боте
команды — так можно поправить прямо за столом.

## Фазы

1. **Схема и ручные участники.** Миграция, несколько персонажей у владельца,
   добавление/удаление/переименование. Отряд наконец собирается целиком.
2. **Характеристики и переопределения** с цепочкой отката. Калькулятор боя
   начинает показывать, сколько персонажей заполнено, а сколько оценено.
3. **Заклинания персонажа.** Лист партии переходит на реальные списки.

Порядок задан зависимостью: смена схемы блокирует остальное.

## Чего не делаем

**Импорт с D&D Beyond.** Открытого API нет, неофициальные точки ломаются.

**Инвентарь и снаряжение.** На «драться или бежать» они влияют через AC и урон,
которые и так вводятся напрямую.

**Разделение известных и подготовленных заклинаний** — см. выше.

## Проверка

* Миграция со старой схемы сохраняет персонажей и их партии — тест на реальной
  последовательности «создать по-старому, открыть по-новому».
* Незаполненный персонаж даёт те же числа, что и сегодня: цепочка отката
  проверяется с обоих концов.
* Лист партии на реальном списке заклинаний отличается от листа по списку
  класса — иначе фаза 3 не имеет смысла.
* Ручной участник участвует в листе партии и в калькуляторе боя наравне с теми,
  кто пользуется ботом.
